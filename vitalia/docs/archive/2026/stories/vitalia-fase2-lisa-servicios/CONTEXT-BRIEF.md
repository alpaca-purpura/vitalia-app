## 14. Free-form notes — what I'd tell a smart colleague
This is a big, well-specified story — the ready package is unusually complete (split BE/FE/agentic arch + a campo-por-campo § Mapa de campos). The trap here is NOT architecture; it's contract drift between the spec's idealized component props and the actually-shipped ui-kit. Burn this in: **RichSelect is `{value,label,description}` + `onValueChange`, not `{value,title,description}` + `onChange`** — the spec and arch-fe both got the prop names wrong. If you copy-paste from the spec you'll get a tsc error or worse, a silent wrong-prop. Same energy with `value_level_catalog.label_es`: those are the engine's e-commerce labels, not the medical escalera labels — the medical strings ("Primera visita" etc.) are FE-local display overrides (RN-2).

The single highest-stakes mechanical risk: **the engine `Offer` aggregate has ~12 required fields with no defaults.** Your `ServiceCatalogService.create` will throw a pydantic ValidationError the first time you call `OfferRepository.create(Offer(...))` if you don't populate `internal_sku`, `headline_promise`, `target_avatar_match`, `pricing_options`, `guarantee_type`, etc. Read `offer.py` and build a sane medical-service default factory. The keystone (AC-6) literally depends on this Offer being valid + `status=ACTIVE` + a `preset_id` that resolves — otherwise `build_identity` won't surface it and Adrián won't know the service exists. That's the whole point of the story, so live-verify it for real (DoD #37): create a service in dev-app, flip Active, then check `build_identity(tenant_id)` actually returns it. Don't trust a GET 200.

There's a cross-story landmine from the embudo work: the kanban-style drag (escalera, T-6) needs `KeyboardSensor` wired with `coordinateGetter: sortableKeyboardCoordinates` — the embudo story shipped this WITHOUT it and a11y broke. AC-8 makes keyboard a11y a hard requirement here.

Cross-module discipline: doctor roster is async + already exists in `clinics`; offer is a fresh module. Wrap clinics via `DoctorRosterPort`, never raw-import — the DDD arch test will fail you. The D-1 sync/async seam (engine OfferRepository is SYNC, your offer services are async) is the fiddliest plumbing — the comunify offer_ladder repo is a decent shape reference but DON'T import it (cross-brand ban). Single-hub: commit by pathspec, bucket `code:offer`.

Finally: Sub-phase B (RAG) is a wall, not a TODO. The autonomous chain STOPS after T-8. Do not start IRAGIndexerPort real binding or the sales_agent retrieval tool — that's `/pm-luana` engine-lift + flagship. The stub indexer is correct for Sub-phase A.
