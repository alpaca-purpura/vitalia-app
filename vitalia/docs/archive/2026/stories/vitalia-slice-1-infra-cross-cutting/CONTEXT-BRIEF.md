## 14. Free-form notes — what I'd tell a smart colleague

This story is a textbook INFRA ENABLER — no user-facing features, no Gherkin scenarios here. Instead, it's the 500+ test GREEN foundation that the next 6 sub-stories (onboarding-wizard, inbox, pipeline, agenda, fidelizacion, marketing) will build on top of.

**Key wins:**
1. **HIPAA-lite enforcement at the DB+code layer.** Dual-filter validation happens automatically via PhiRepositoryBase (architectural, not human discipline). Audit log sync write is enforced (sync NOT async). Sanitization at trace-emit time (not retroactive). If someone writes a query and forgets `clinic_id` filter, the code will fail the arch test. This is defensive-in-depth.

2. **Design tokens as source of truth for brand colors.** Post-fix (4545c22), zero color hex/hsl values live in TSX files. Everything flows from globals.css CSS vars consumed by tailwind. When the brand changes a color, one edit to globals.css + one tailwind rebuild = all 12 Storybook stories + production repaint. No hunting through 47 files for hardcoded `#c2a6ff` literals.

3. **Registries future-proof the dispatch pattern.** Payment providers / fiscal adaptations / appointment origins are now brand-config data (not hardcoded logic). When Slice 2 payment adapter lands, it just registers a new slot; no core code changes. This is the Extension SDK pattern materialized in vitalia's medical vertical.

4. **Workers scaffold is honest about Slice 1 boundaries.** All 11 cron jobs raise NotImplementedError pointing at the side story that will implement them. I've seen teams ship "scaffold" code that silently no-ops; this one fails loud. That's better for visibility.

**Things an auditor must verify (beyond validators GREEN):**

1. **Dual filter is enforced everywhere PHI is read/written.** I spot-checked T-infra-9 IAM/CRM: PatientRepository extends PhiRepositoryBase (✓), LeadRepository does NOT (✓ — correct, Lead is non-PHI). But also check: is there a query like `session.execute(select(Patient).where(Patient.tenant_id == tenant_id))` without clinic_id anywhere? The arch test catches it, but eyeballs matter too.

2. **Audit log row creation is sync, not async.** Look at the implementation of `AuditLogRepository.write()` — does it await? If it's `fire_and_forget`, PHI may be leaked before the audit row is written. T-infra-3 spec says sync, but implementation should verify.

3. **OTel graceful degradation is not a free pass.** Yes, it skips tests when SDK is absent. But production MUST have the SDK installed. The sentinel pattern is insurance, not business-as-usual. Verify the production Docker image includes `opentelemetry-sdk`.

4. **Storybook stories are not production data.** I see 6 Storybook .stories.tsx files with vt-* token classes (they're allowed because they're view-only). But the 3 production component files (AttributionMatrixWidget, MarketingBowtieSVG, WizardChatThread) should have ZERO hsl/hex literals. The arch test verified; double-check visually if time allows.

5. **Registries placeholder graceful failure.** If a cron job or tool handler tries to use payment_provider_registry but a slot is NotImplementedError, what happens? The exception should bubble up with clear context (which is the current design). Edge case: if a clinic somehow has a payment method whose enum value doesn't match any registry slot, does the code fail or silently lose the transaction? Check error paths.

**One more thing:** The defer_audit lift 2026-05-18 came with Chris ratification that color refactoring is NON-NEGOTIABLE (zero ratchet allowlists for hardcoded colors). That's good discipline. But it also means the 6 Storybook .stories.tsx files that still have hsl() literals in gradient definitions (within globals.css vt-* utility classes, exempt by spec) are dancing on the edge. Post-merge, watch that the styling remains coherent. If 3 months from now we realize Storybook stories have visual glitches because the gradients' hsl() was subtly different from what tailwind interprets, we'll know why.
