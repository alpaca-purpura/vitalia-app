## Findings

### WARN: Visual baseline tolerance too generous

**Category:** 10 (Tests/TDD) — gates against meaningful regressions
**File:** `vitalia/frontend/e2e/visual/visual-smoke.spec.ts:63, 93, 131`
**Issue:** All three screenshot assertions use `maxDiffPixelRatio: 0.2` (20% of pixels allowed to differ). This is **very generous** — 20% pixel diff allows entire UI sections to change without flag.

Per spec § 3 SC-16: "And if diff > 0.2 threshold (allow minor Clerk dev mode UI updates): test FAILS". The spec uses 0.2 as the threshold, but ambiguous wording — likely intent was 0.2% (`0.002`) or `maxDiffPixels: 200` (absolute pixels, more deterministic for layout regression).

For sign-in form (Clerk vendor UI), some tolerance is justified (Clerk dev mode iconography updates). But 20% pixel drift could hide entire form field repositioning. Per `tessl__react-patterns` + `playwright-expert/references/anti-patterns.md` ("visual regression with overly-generous threshold = noise gate, not signal gate"), this baseline is at risk of being meaningless.

**Recommendation:**
- `/sign-in` + `/sign-up` (Clerk vendor UI): `maxDiffPixelRatio: 0.05` (5%) or `maxDiffPixels: 5000` absolute (allow Clerk theme updates without OUR UI regressions slipping through)
- `/` dashboard (our UI): `maxDiffPixelRatio: 0.02` (2%) — stricter for code we own
- Use `mask: [...]` aggressively for genuinely dynamic regions (timestamps, user avatars, clerk-captcha) — already done line 66-70, 95-99, 134-138 ✅

**Fix:** Adjust thresholds per page sensitivity. Document baseline regen process if Clerk UI updates legitimately push past threshold.

**Skill ref:** `playwright-expert/references/anti-patterns.md` § visual regression. Spec § 3 SC-16 wording suggests intent was a stricter gate.

### WARN: audit script regex catches HTTP codes inside test output text

**Category:** 4 (Code Quality) / 10 (Tests)
**File:** `scripts/playwright_console_network_audit.sh:215-217`
**Issue:** Text fallback `audit_report_text` regex `grep -oE '\b[45][0-9]{2}\b'` will match any 3-digit number 400-599 in test output — including legitimate values like "499 users" or "503 ms latency" in logs. False positives possible. Network audit via trace.zip parsing (`audit_trace_zip`, line 102-197) is the canonical path; text fallback is best-effort.

**Mitigation:** Current path is acceptable since trace.zip parsing is preferred (line 257-262); text fallback only runs if no trace.zip found (line 264-268). Document this in script header.

**Fix:** Add comment to script header that text fallback is a coarse heuristic and trace.zip via Playwright `--trace=on` is the SSoT. Acceptable as-is for warm-path coverage.

### WARN: a11y test excludes Clerk iframe globally

**Category:** 5 (Accessibility)
**File:** `vitalia/frontend/e2e/a11y/a11y-smoke.spec.ts:51, 81`
**Issue:** `.exclude("iframe")` excludes ALL iframes from axe scan, not just Clerk's. If future iframe-embedded vendor (Stripe checkout, etc.) is added without setting up axe-aware exclusion, a11y violations inside that iframe will silently pass.

**Recommendation:** Use more specific exclusion targeting only the Clerk iframe selector. Per axe-core docs: `.exclude({ selector: 'iframe[src*="clerk"]' })` or similar Clerk-specific match.

**Fix:** Update to specific exclusion:
```typescript
const results = await new AxeBuilder({ page })
  .exclude({ fromShadowDom: ['iframe[src*="clerk"]', '#clerk-captcha-iframe'] })
  .analyze();
```

**Skill ref:** axe-core docs + spec § 3 SC-14 wording: "Excludes Clerk iframe to avoid bot-detection false-positives" (specific intent).
